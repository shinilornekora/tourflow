# Модель размещения и изоляция данных (РХД ПР-2)

## Кто арендатор

В TourFlow два вида «чужих» данных:

- **отель** — арендатор для менеджеров: менеджер отеля А не должен видеть брони и аудит отеля Б и менять его каталог;
- **клиент** — владелец своих броней, ключей идемпотентности и уведомлений.

## Модель размещения — общая

Строки всех отелей и клиентов лежат в одних таблицах (shared schema), изоляция — политиками RLS. Сравнение по пяти критериям ПР-2:

| Критерий | Общая схема (выбрано) | Схема на отель | База на отель |
|---|---|---|---|
| Стоимость | одна база и один пул на сервис | сотни схем, миграция каждой | сотни баз, пул на каждую — не помещается в `max_connections` |
| Требования регуляторов | данные бронирований и контакты; отдельного хранения по закону не требуют | — | нужна, только если сеть отелей потребует физического разделения |
| Восстановление после сбоя | один бэкап; вернуть один отель на вчера нельзя без выборочного восстановления | можно восстановить схему отеля | можно восстановить базу отеля |
| Перегруженный арендатор | «шумный» отель влияет на соседей; защита — лимиты gateway, пул, блокировки только по строкам своего отеля | то же: общий сервер | изолирован |
| Ожидаемое число арендаторов | сотни отелей и десятки тысяч клиентов — подходит | до десятков отелей | единицы крупных клиентов |

Клиентов десятки тысяч, поэтому для них выделенная модель невозможна в принципе. Для отелей она возможна, но не оправдана: замер (`docs/LOAD.md`) показывает, что одна «горячая» категория выдерживает ~480–560 броней в секунду, и узкое место — процессор, а не соседи.

**Цена общей модели:** ошибка в политике RLS открывает данные всех сразу. Поэтому — `FORCE`, `WITH CHECK`, отдельная роль данных и отрицательные тесты.

**Пересмотреть, если:** появится сеть отелей с договорным требованием отдельного хранения или отель, чья нагрузка мешает остальным. Тогда смешанная модель: такие арендаторы — в выделенной базе, остальные — в общей.

## Два уровня принуждения

| Уровень | Что делает | Где |
|---|---|---|
| 1. Приложение | актор берётся только из проверенного JWT (и в gateway, и в сервисе); правила домена: `Reservation.CanView`, `Cancel`, `Hotel.CanEdit`; списки броней и аудита менеджера сервис ограничивает его отелями (`managerScope`) | `platform/auth`, `*/domain`, `booking/app` |
| 2. PostgreSQL | RLS с `FORCE` под ролью данных `*_app`, которая таблицами не владеет: снять политику, удалить триггер аудита, прочитать outbox, изменить реплику каталога (кроме служебного столбца `row_lock`, нужного для `FOR SHARE`) или удалить бронь она не может | миграции, `migrations/embed.go`, `platform/pg/roles.go` |

Уровни проверяются по отдельности. `TestManagerScopeWithoutRLS` выключает политики и убеждается, что уровень 1 сам не отдаёт чужому менеджеру ни броней, ни аудита. `TestNegativeTenancy` идёт прямым SQL мимо сервиса и проверяет уровень 2. В первой версии списки менеджера фильтровала одна RLS (D10).

Контекст RLS — `set_config('app.user_id' / 'app.role', …, true)` в начале каждой транзакции: он действует до её конца и не переходит к следующему запросу на том же соединении пула (T40).

## Что закрыто RLS

| Сервис | Таблица | Политика |
|---|---|---|
| booking | `reservations` | свои брони клиента; брони своего отеля — менеджеру; всё — admin и system |
| booking | `audit_log` | читать — менеджеру своего отеля и admin; писать — только от имени настоящего актора и только о своём: менеджер — в журнал своего отеля, клиент — о собственной брони, записи об отеле (`hotel.*`) — только служебный процесс (`003`, `004`); менять и удалять нельзя (права + триггер) |
| booking | `idempotency_keys` | только свои ключи; чужие — только служебной очистке |
| booking, catalog | `outbox` | читать и отмечать — только ретранслятор под ролью владельца. Добавлять: в booking — только событие о брони, которую автор видит, и только согласованное с ней (отель и клиент в конверте — как у брони); в catalog — любой код сервиса |
| catalog | `hotels`, `room_types` | читать может любой (витрина публична); менять — admin или менеджер этого отеля; статус отеля — только admin (триггер) |
| catalog | `hotel_managers` | читать может любой; назначать и снимать — только admin. Это источник прав RLS в booking |
| notification | `notifications` | читать, отмечать прочитанным и удалять — только адресат; создавать — обработчик событий (system). Политика одна на все операции, поэтому адресат формально может вставить уведомление самому себе — другому не может |

## Что RLS не закрывает — и почему

- **`inventory` (остатки).** Это не тайна арендатора: свободные номера показываются всем на витрине. Изменить остатки чужого отеля мешает уровень 1 (бронь создаётся только через сценарий) и отсутствие у клиента прямого доступа к базе. Записано как осознанный выбор (T112).
- **Реплики каталога в booking** (`hotel_replica`, `room_type_replica`). Публичные данные каталога. Защищены правами: пишет только проекция событий под владельцем; у роли данных — чтение и `UPDATE` одного служебного столбца `row_lock` (без него PostgreSQL не даёт `SELECT … FOR SHARE`). Цену, вместимость, статус и версию она изменить не может — проверено тестом.
- **`hotel_manager_replica`.** Данные не публичные (состав менеджеров клиентам не показывается), и это источник прав для всех политик (`app_can_see_hotel`). Политики на ней нет, но запись у роли данных отозвана целиком: назначить себя менеджером код запроса не может. Чтение оставлено — цена записана в T112.
- **identity (`users`, `refresh_tokens`).** Сервис почти всегда читает по ключу из запроса (вход по email, обновление токена) до того, как появится личность. Изоляция — уровнем приложения и отдельной базой, куда чужие роли не подключаются. Политик RLS нет, но роль данных есть и здесь: запросы идут под `identity_app`, которая не может менять схему (T111).
- **Подмена контекста.** Политики доверяют настройке `app.user_id`, а выставляет её сам код сервиса. Код, который выполнит `set_config` с чужим идентификатором — ошибка или SQL-инъекция под ролью данных, — увидит чужие строки. RLS защищает от забытого условия и от снятия политики, но не от кода, который сознательно выдаёт себя за другого. От этого защищает уровень 1: идентификатор приходит только из проверенного токена, все запросы параметризованы. То же относится к записи: выставив `app.role = 'admin'`, такой код допишет запись аудита от имени администратора. Не проходит только служебный контекст: `system` в booking действует лишь под владельцем таблиц.
- **Поддельное событие.** В catalog вставка в outbox не ограничена: скомпрометированный код может дописать событие, которого не было, — в том числе событие с чужим списком менеджеров, которое дойдёт до реплики booking. В booking вставка сужена политикой (событие — только о своём), но подмена контекста обходит и её (T118). Сам брокер без аутентификации и ACL: в топик может писать любой процесс внутренней сети (T83).
- **Notification: inbox и версии.** Обработчик событий там работает под ролью данных, поэтому `processed_events` и `reservation_versions` открыты ей на запись: код запросов мог бы удалить отметку обработки или поднять версию и подавить уведомление. В booking эти таблицы закрыты — там проекция идёт под владельцем (T111). По той же причине служебный контекст там доступен роли данных: под `notification_app` с `app.role = 'system'` читаются уведомления всех адресатов. В booking он привязан к владельцу таблиц, в notification — нет: обработчик событий сам работает под ролью данных.
- **Аудит вне booking.** В catalog и identity журнала нет: кто назначил менеджера или выдал роль, по базе не узнать (T124). Автор отключения отеля доезжает до аудита booking в событии.
- **Владелец базы.** Роль `*_svc` может снять `FORCE`, удалить политику и триггер аудита. Под ней работают миграции, ретранслятор, проекция каталога и служебные задачи того же процесса. В бою пароль владельца выдают только шагу выкладки.

## Отрицательные тесты

Все идут прямым SQL под ролью данных, «в обход» сервиса (`TEST_PG_APP_DSN`):

| Тест | Что проверяет |
|---|---|
| `booking/tenancy_test.go` → `TestNegativeTenancy` | восемь групп: чужое не читается; чужое не меняется и не удаляется; строку за другого не записать (`WITH CHECK`, код 42501); аудит не подделать от чужого имени; в журнал чужого отеля не дописать даже от своего имени, а записи `hotel.*` — никому, кроме служебного процесса; без контекста — ноль строк; роль данных не снимает RLS, не читает outbox, не пишет реплику менеджеров и inbox, не подменяет её временной таблицей, не объявляет себя служебным процессом, не меняет цену, вместимость и статус в реплике каталога, не удаляет брони |
| `booking/tenancy_test.go` → `TestManagerScopeWithoutRLS` | уровень приложения отдельно от базы: при выключенных политиках чужой менеджер получает пустые списки броней и аудита, свой — видит |
| `booking/outbox_test.go` → `TestOutboxForeignEventRejected` | событие о чужой брони в outbox не записать: чужой клиент, менеджер другого отеля, запрос без контекста — 42501; не записать и событие, противоречащее брони (несуществующая бронь, чужой клиент в полезной нагрузке), даже под честным контекстом менеджера или владельца; владелец брони и менеджер её отеля правдивое событие записать могут |
| `identity/integration_test.go` → `TestDataRoleCannotChangeSchema` | роль данных identity не создаёт таблиц, не меняет схему, не делает `TRUNCATE` |
| `booking/integration_test.go` → `TestRowLevelSecurity` | то же через сервис + контекст не утекает через пул |
| `booking/integration_test.go` → `TestAuditIsAppendOnly` | роль данных: UPDATE/DELETE/TRUNCATE аудита и отключение триггера — 42501; владелец со снятым `FORCE` упирается в триггер |
| `catalog/integration_test.go` → `TestCatalogRLSNegative` | менеджер не меняет чужой отель, не создаёт в нём категорию, не назначает себя; в своём отеле не добавляет со-менеджера и не меняет статус (это права администратора); клиент и запрос без контекста не создают отели; временной таблицей источник прав не подменить |
| `notification/integration_test.go` → `TestNotificationsIsolatedByRLS` | чужие уведомления не видны и не меняются, без контекста — ноль, написать другому нельзя |

В каждом тесте есть положительный контроль: владелец строки её видит. Иначе «ноль строк у чужого» ничего бы не доказывал.
